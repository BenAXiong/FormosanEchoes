# DATA_SCHEMA.md — Field Reference

Authoritative description of the Supabase database schema and the admin-layer types that sit on top of it.
For the *why* behind design choices, see `docs/DECISIONS.md`.

> **Architecture note:** `data/songs.json` and `data/artists.json` are gone. Supabase PostgreSQL is the sole source of truth. `data/controlled-vocab.json` remains as a reference document only — it is not imported at runtime.

---

## Database tables

### `songs`

Master catalog. One row per recording.

| Column | Type | Notes |
|---|---|---|
| `id` | `UUID PK` | Generated by Supabase. |
| `legacy_id` | `TEXT UNIQUE` | Old `sof-NNNNN` IDs from migration — kept as a bridge, not used in new code. |
| `yt_title` | `TEXT` | Raw YouTube video title at time of import. **Provenance only — never edited.** |
| `title_original` | `TEXT` | Curated accurate title. Romanized or indigenous script only — no Chinese characters. Sentence case. If only a Chinese title exists, leave `null` and use `title_zh`. |
| `title_zh` | `TEXT` | Official Chinese name from album/artist page/KKBOX/Spotify. Do not put AI-translated Chinese here. |
| `title_en` | `TEXT` | English title, if one has been formally published. |
| `artist_credit` | `TEXT` | Raw credit string as it appears on the recording ("ABAO feat. X"). Preserved exactly — do not normalize. Used as display fallback when no artist is linked. |
| `yt_url` | `TEXT` | Full YouTube watch URL. |
| `yt_video_id` | `TEXT` | Extracted YouTube video ID (11-char string). Used for thumbnail and embed. |
| `yt_channel` | `TEXT` | YouTube channel name at import time. |
| `yt_channel_id` | `TEXT` | YouTube channel ID. |
| `yt_upload_date` | `DATE` | Upload date from YouTube metadata. |
| `yt_views` | `INTEGER` | View count snapshot at import. |
| `yt_duration` | `INTEGER` | Duration in seconds. |
| `yt_thumbnail_url` | `TEXT` | Thumbnail URL. |
| `yt_description` | `TEXT` | YouTube description at import time. |
| `url` | `TEXT` | Non-YouTube source URL (Spotify, SoundCloud, archive, etc.). Never store a YouTube URL here — the admin UI strips it. |
| `album` | `TEXT` | Album or compilation name. |
| `year` | `TEXT` | Release year. Stored as text to allow uncertain values (e.g. `"~1980"`). |
| `language` | `TEXT` | Language of the song. Must match `data/controlled-vocab.json → languages`. One of the 16 official Formosan group names. |
| `ethnic_group` | `TEXT` | Cultural/ethnic tradition the song belongs to. May differ from the performer's background. Controlled vocab. |
| `region` | `TEXT` | Broad geographic region (e.g. "Eastern Taiwan"). |
| `location` | `TEXT` | Specific village or location associated with the song. |
| `genre` | `TEXT` | One of: `Traditional`, `Traditional Choral`, `Modern Folk`, `Contemporary Folk`, `Contemporary Indigenous Folk-Pop`, `Indigenous Gospel / Folk`. |
| `recording_type` | `TEXT` | One of: `Studio`, `Live`, `Home Recording`, `Field Recording`. |
| `description` | `TEXT` | Public-facing context shown to visitors on the song detail panel. |
| `notes` | `TEXT` | Internal admin/curation notes. Not shown publicly. |
| `verification_status` | `TEXT DEFAULT 'candidate'` | Curation workflow state. One of: `candidate`, `needs_review`, `checked`, `approved_public`, `approved_private`, `rejected`, `duplicate`. |
| `created_at` | `TIMESTAMPTZ` | Row creation timestamp. |

### `lyrics`

One-to-one with `songs`. A song has at most one lyrics row. Absence of a row means no lyrics attempt has been made.

| Column | Type | Notes |
|---|---|---|
| `song_id` | `UUID PK FK→songs` | Matches the parent song. |
| `lyrics_original` | `TEXT` | Full lyrics in the indigenous language (romanized script or native orthography). |
| `lyrics_zh` | `TEXT` | Traditional Chinese translation. |
| `lyrics_en` | `TEXT` | English translation. |
| `source` | `TEXT` | Where the lyrics came from. Human-readable (album booklet, MoJim URL, artist website, etc.) or the `[not found — AI YYYY-MM-DD]` sentinel. See sentinel rules below. |
| `show_publicly` | `BOOLEAN DEFAULT FALSE` | **The render gate.** Lyrics are never shown to public visitors unless this is `true`. Gemini-enriched lyrics always arrive with `false`. A human must set this to `true` in the admin Song Audit panel. |
| `created_at` | `TIMESTAMPTZ` | Row creation timestamp. |

#### `lyrics.source` sentinel system

The `source` field doubles as a search-attempt log:

- `null` — no lyrics row exists: lyrics have never been searched for this song.
- `"[not found — AI YYYY-MM-DD]"` — AI searched but found nothing. Date records when. The `missing` badge for this song will show `lyrics` (needs content) not `lyrics_unapproved`, since searching again may be wasteful.
- Any other string — actual source reference (album, URL title, etc.).

This distinction prevents redundant re-research on songs the AI already couldn't find lyrics for.

### `artists`

One row per artist, group, or ensemble.

| Column | Type | Notes |
|---|---|---|
| `id` | `UUID PK` | Generated by Supabase. |
| `legacy_id` | `TEXT UNIQUE` | Old `art-NNN` IDs — migration bridge only. |
| `name_display` | `TEXT NOT NULL` | Primary display name used in all UI. |
| `ethnic_groups` | `TEXT[] DEFAULT '{}'` | Multi-value. An artist can span two groups. Each value must match controlled vocab. |
| `language` | `TEXT` | Primary language of this artist's repertoire. |
| `dialect` | `TEXT` | Dialect sub-tag (deferred; not surfaced in UI yet). |
| `is_group` | `BOOLEAN DEFAULT FALSE` | `true` for ensembles, choirs, bands. |
| `active_years` | `TEXT` | Free text: `"1990–2010"`, `"2005–present"`. |
| `bio_zh` | `TEXT` | Chinese-language biography. |
| `bio_en` | `TEXT` | English-language biography. |
| `bio_ycm` | `TEXT` | Internal curation notes — not shown publicly. |
| `zh_surname` | `TEXT` | Chinese surname, for disambiguation. |
| `youtube_channel` | `TEXT` | YouTube channel URL. |
| `wikipedia_url` | `TEXT` | Wikipedia article URL. |
| `photo_url` | `TEXT` | External image URL (sourced manually). No image upload infra — external URL only. |
| `sources` | `TEXT[]` | Provenance URLs and references used to compile this record. |
| `notes` | `TEXT` | Internal disambiguation notes. |
| `created_at` | `TIMESTAMPTZ` | Row creation timestamp. |

### `artist_names`

All name aliases per artist. Used for search, linking, and display.

| Column | Type | Notes |
|---|---|---|
| `id` | `UUID PK` | |
| `artist_id` | `UUID FK→artists` | |
| `name` | `TEXT NOT NULL` | The name variant. |
| `script` | `TEXT NOT NULL` | One of: `'zh'` (Chinese/hanzi), `'en'` (Latin-script), `'ab'` (indigenous/aboriginal name in the language's own form). |

**Script semantics:**
- `'zh'` — Chinese characters. First row = official display name; subsequent = aliases/variants.
- `'en'` — Latin-script names: romanized forms, English-language names, and any Latin-alphabet variants. First row = canonical; subsequent = spelling variants.
- `'ab'` — The name as it appears in the indigenous language itself (aboriginal/indigenous form). Each of the 16 Formosan peoples has its own orthographic conventions; do not assume a single shared script system.

Row order within a script = priority. The first `'ab'` or `'en'` name is the canonical form for display; the first `'zh'` is the canonical Chinese name. No extra "is_primary" flag.

**Display priority:** `ab` > `en` > `zh`. The `artist_display` field is computed as `{ab ?? en} - {zh}`.

**Important:** The old codebase used `'ab'` for Latin-script names (incorrectly). A migration renamed all such rows to `'en'`. Do not re-introduce `'ab'` for names that are simply Latin-alphabet spellings of the artist's name.

### `song_artists`

Many-to-many: song ↔ artist.

| Column | Type | Notes |
|---|---|---|
| `song_id` | `UUID FK→songs` | |
| `artist_id` | `UUID FK→artists` | |

Primary key is `(song_id, artist_id)`.

Group membership links.

| Column | Type | Notes |
|---|---|---|
| `group_artist_id` | `UUID FK→artists` | The group. |
| `member_artist_id` | `UUID FK→artists` | The individual member. |

Primary key is `(group_artist_id, member_artist_id)`.

### `tags` + `song_tags`

`tags` — vocabulary table.

| Column | Type | Notes |
|---|---|---|
| `id` | `UUID PK` | |
| `value` | `TEXT UNIQUE` | Slug: `"love-song"`, `"ceremonial"`, `"lullaby"`. |
| `label` | `TEXT` | Display string: `"Love Song"`. |

`song_tags` — many-to-many join.

| Column | Type | Notes |
|---|---|---|
| `song_id` | `UUID FK→songs` | |
| `tag_id` | `UUID FK→tags` | |

**Tag rules:**
- Tags describe content themes or context not already expressed in dedicated fields.
- Do **not** tag with the language name, ethnic group, or genre — those have their own columns.
- Valid example tags: `ceremonial`, `lullaby`, `love-song`, `choral`, `children`, `harvest`, `wedding`.

## Admin-layer types

These types live in `components/admin/SongsAdminView.tsx` and are not exported. They represent the admin panel's internal data model, not the database directly.

### `AdminSong`

The shape returned by `GET /api/admin/unaudited-songs`. One entry per song in the admin list.

```typescript
type AdminSong = {
  id: string;
  title: string;                  // computed: title_original ?? title_zh ?? yt_title ?? '(untitled)'
  yt_title: string | null;
  title_original: string | null;
  title_zh: string | null;
  title_en: string | null;
  artist_credit: string;          // raw DB string
  artist_display: string | null;  // computed from song_artists join: "RomanizedName - 中文名" per linked artist, joined by " × "
  yt_url: string;
  yt_video_id: string | null;
  url: string | null;             // non-YouTube URL only
  language: string | null;
  ethnic_group: string | null;
  region: string | null;
  location: string | null;
  genre: string | null;
  recording_type: string | null;
  year: string | null;
  album: string | null;
  description: string | null;
  notes: string | null;
  verification_status: string | null;
  tags: string[];
  lyrics_original: string | null;
  lyrics_zh: string | null;
  lyrics_en: string | null;
  lyrics_show_publicly: boolean;
  missing: string[];              // computed badges (see below)
};
```

**`artist_display` format:** For each linked artist, the join resolves `artist_names` and produces `"EnglishName - 中文名"` (or just one if only one script exists). Multiple artists are joined with ` × `. Falls back to `null` if no artist is linked — `artist_credit` is the display fallback in that case.

#### `missing` badges

Computed server-side in the `/api/admin/unaudited-songs` route. Never stored as a DB column.

| Badge | Condition |
|---|---|
| `language` | `songs.language` is null |
| `ethnic_group` | `songs.ethnic_group` is null |
| `no_artist` | `songs.artist_credit` is null or empty |
| `no_url` | `songs.yt_url` is empty AND `songs.url` is null |
| `lyrics` | No lyrics row exists, OR lyrics row exists but has no content AND source is not a `[not found` sentinel |
| `lyrics_unapproved` | Lyrics content exists but `lyrics.show_publicly` is `false` |

### `DraftForm`

The internal form state for the right-panel song editor. All fields are strings (empty string = unfilled), except `lyrics_show_publicly` which is boolean.

```typescript
type DraftForm = {
  yt_title: string;
  title_original: string;
  title_zh: string;
  title_en: string;
  artist_credit: string;
  url: string;            // non-YouTube URL only (YouTube URLs are stripped from this field on load)
  language: string;
  ethnic_group: string;
  region: string;
  location: string;
  genre: string;
  recording_type: string;
  year: string;
  album: string;
  description: string;
  notes: string;
  verification_status: string;
  tags: string;           // comma-separated tag values
  lyrics_original: string;
  lyrics_zh: string;
  lyrics_en: string;
  lyrics_source: string;  // always '' on initial load from DB; populated by AI research or manual edit
  lyrics_show_publicly: boolean;
};
```

**`draftFromSong(s: AdminSong) → DraftForm`** — Converts a fetched `AdminSong` into a blank-form-safe draft. Key behaviors:
- `url`: strips YouTube URLs (songs.url sometimes contained a YT link from early import; it belongs in `yt_url`, not `url`).
- `lyrics_source`: always initialised to `''` — the DB value is write-only from the admin perspective; it is not loaded back into the form field (to avoid accidentally re-saving stale source labels).

## Admin research workflow

### Three save paths

The admin panel has three distinct ways to save enriched data. They use different API paths with different field mappings.

#### Path 1 — Single-song manual save (`saveSelected`)

Triggered by the "Save Changes" button in the right panel. Sends `{ song_id, fields: DraftForm }` to `POST /api/admin/update-song`.

- Writes all `DraftForm` fields to `songs` and `lyrics` tables.
- Tags are replaced entirely: delete all `song_tags` for this song, re-insert from `tags` comma string.
- `lyrics` row is upserted only if at least one of `lyrics_original`, `lyrics_zh`, `lyrics_en`, or `lyrics_source` is non-empty.
- `show_publicly` is written as-is from the draft checkbox.

#### Path 2 — Batch review save (`saveBatchSong`)

Triggered when the user clicks "Save" on an individual song card in the left-rail batch checklist. Same API endpoint and field mapping as Path 1, but draws from the song's `BatchEntry.draft` rather than the right-panel `draft` state.

#### Path 3 — Research All auto-save (`saveAllResearched`)

Triggered by "Save All Researched". Sends `{ song_id, enriched: GeminiResult }` to `POST /api/admin/update-song`. Uses the `enriched` branch of the route (not `fields`). Key differences from Paths 1 & 2:

- Only writes fields that are present and non-null in the AI result — blank fields in the AI response do not overwrite existing DB values.
- `lyrics.show_publicly` is always set to `false` — auto-saved AI lyrics are never made public automatically.
- `lyrics.source` is set to the sentinel `[not found — AI YYYY-MM-DD]` when the AI found no lyrics, ensuring the attempt is recorded even if no lyrics row content is written.

### Research merge strategy (`mergeEnriched`)

When AI research results return, they are merged with the current form draft using:

```typescript
function mergeEnriched(base: DraftForm, e: AIResult): DraftForm {
  return {
    ...base,                          // everything not listed below comes from base
    title_original: (e.title_original && !hasChinese(e.title_original))
                     ? e.title_original : base.title_original,
    title_zh:        e.title_chinese         ?? base.title_zh,
    language:        e.language_claimed      ?? base.language,
    ethnic_group:    e.ethnic_group_claimed  ?? base.ethnic_group,
    genre:           e.genre                 ?? base.genre,
    recording_type:  e.recording_type        ?? base.recording_type,
    year:            e.year                  ?? base.year,
    album:           base.album,             // AI never overwrites album
    notes:           e.notes                 ?? base.notes,
    lyrics_original: e.lyrics_original       ?? base.lyrics_original,
    lyrics_zh:       e.lyrics_translation_zh ?? base.lyrics_zh,
    lyrics_en:       e.lyrics_translation_en ?? base.lyrics_en,
    lyrics_source:   e.lyrics_source         ?? base.lyrics_source,
    tags:            e.tags                  ?? base.tags,
  };
}
```

**Merge priority:** AI value wins if non-null. Base (draft) value is used as fallback when AI returns null.

**`base` is always the current `draft` state** — not the original DB values. This means:
- Manual edits made before re-researching are preserved as the fallback.
- Deliberately corrected fields (e.g. artist_credit changed from wrong to right) survive a re-research if the AI returns null for that field.
- If the AI returns a non-null value, it still wins — so AI corrections of bad manual entries work as expected.

**`title_original` guard:** `hasChinese()` prevents Chinese characters from landing in `title_original`. If the AI only found a Chinese title, it goes to `title_zh` instead.

**Research call context:** The fetch to `/api/admin/enrich-song` sends `draft.artist_credit` (not the DB value) as the `artist_credit` parameter, and prefers `draft.title_original || draft.title_zh` over `yt_title` as the `title` parameter. This means corrections typed into the form before clicking Research are sent to the AI as context.

### Research button state machine

The right-panel research button has three states:

| State | Appearance | Meaning |
|---|---|---|
| `idle` (not yet researched) | Violet `✦ Research with AI` button | Default; song has not been researched this session. |
| `researching` | Red `◼ Stop` button | Fetch in progress; click aborts. |
| `idle` (post-research) with `songResearched = true` | Blue `✓ Complete — review & save` div | Research finished; draft has been updated; user should review and save. |

The blue "complete" state persists until the user manually edits a field, selects a different song, or saves.

### Grounding sources

After each `/api/admin/enrich-song` call, `sources` state is set to an array of `{ url: string; title: string | null }` objects extracted from Gemini's `groundingMetadata.groundingChunks`. These are displayed as pills below the form.

- `title` is the human-readable site name returned by Gemini (e.g. "Klokah 族語E樂園"). Always prefer this as the pill label over the raw URL.
- `url` is a Vertex AI proxy redirect (`vertexaisearch.cloud.google.com/…`) — expiring, not storable long-term, but functional as a click target in the current session.
- The first source's `title` is promoted to `lyrics_source` when Gemini found lyrics but its own `lyrics_source` field only says something generic like "AI research — date".

## `lib/types.ts` vs. actual DB columns

The `Song` interface in `lib/types.ts` is partially legacy — it was designed for the old JSON-file architecture and contains fields that have no corresponding DB column. `mapSong` in `lib/db.ts` sets these to `undefined`. They exist only to avoid TypeScript errors until the interface is formally pruned.

Legacy fields with no DB backing (all `undefined` at runtime):
`language_evidence`, `ethnic_group_evidence`, `performers`, `source_platform`, `lyrics_url`, `source_snippets`, `verification_notes` (mapped from `notes`), `confidence` (hardcoded `'unknown'`), `needs_manual_verification` (hardcoded `true`), `checked_by_me` (hardcoded `false`), `title_romanized`, `lyrics.lyrics_romanized`, `lyrics.lyrics_rights_status`, `lyrics.lyrics_notes`, `lyrics.has_permission` (mirrors `show_publicly`).

These are safe to read (they return `undefined` gracefully) but should not be written to or relied on for logic.

`title_romanized` and `lyrics_romanized` deserve a note: they were designed as separate pronunciation-guide fields (e.g. CIP romanization for learners), but most Formosan languages already use Latin-based orthography, so `title_original` IS already in Latin script for the majority of songs. The fields were never given DB columns and are never populated. They are candidates for removal from `lib/types.ts` in a future cleanup.

## Public-safe vs. internal-only fields

Fields shown to public visitors (gated by `songs.verification_status` and `lyrics.show_publicly`):

- All title fields
- `artist_credit` (display name, not internal IDs)
- `language`, `ethnic_group`
- `genre`, `tags`, `year`, `region`
- `description`
- `lyrics.*` — **only if `lyrics.show_publicly === true`**
- `yt_url` (embedded player)

Internal/admin-only:
- `notes` (curation notes)
- `verification_status` (workflow state)
- `yt_title`, `yt_channel`, `yt_description` (raw YouTube provenance)
- `legacy_id`
- `artist_display` (computed join, not a DB column)
- `missing` badges
- `lyrics.source`, `lyrics.show_publicly` (set in Song Audit panel only)

## Controlled vocabulary

Canonical values live in `data/controlled-vocab.json`. Do not invent values outside these lists.

| Key | Used in |
|---|---|
| `languages` | `songs.language`, `artists.language` |
| `ethnic_groups` | `songs.ethnic_group`, `artists.ethnic_groups[]` |
| `confidence_levels` | (legacy — `confidence` column no longer on songs table) |
| `verification_statuses` | `songs.verification_status` |

The 16 official Formosan languages/groups: Amis (Pangcah), Atayal, Paiwan, Bunun, Puyuma, Rukai, Tsou, Saisiyat, Tao (Yami), Thao, Kavalan, Truku, Sakizaya, Seediq, Hla'alua, Kanakanavu.

`"Amis"` is the correct controlled-vocab value for Amis/Pangcah. Do not use `"Pangcah"` or `"Formosan"`.
